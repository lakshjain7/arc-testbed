### A5. Hardware requirements — 24 GB is realistic, 16 GB is not

**Stated requirement** ([wiki FAQ](https://github.com/FudanSELab/train-ticket/wiki/FAQ), [Installation Guide](https://github.com/FudanSELab/train-ticket/wiki/Installation-Guide)):
> docker-compose: **at least 24GB memory and 50GB disk** on Linux.
> Kubernetes+Istio: **at least four same-configuration Linux servers.**

⚠️ **The wiki Installation Guide is stale.** It references `ts-deployment-part1/2/3.yml` (files that no longer exist), k8s v1.14, and Istio v1.0.0 — all pre-v1.0.0-reconstruction. Ignore its procedure; keep only its RAM figure.

Sources: [`deploy.yaml.sample`](https://github.com/FudanSELab/train-ticket/blob/master/deployment/kubernetes-manifests/quickstart-k8s/yamls/deploy.yaml.sample), [mysql chart values](https://raw.githubusercontent.com/FudanSELab/train-ticket/master/deployment/kubernetes-manifests/quickstart-k8s/charts/mysql/values.yaml), [nacos chart values](https://raw.githubusercontent.com/FudanSELab/train-ticket/master/deployment/kubernetes-manifests/quickstart-k8s/charts/nacos/values.yaml).

**`--independent-db` is fatal on a laptop:** 24 MySQL clusters × 3 pods = **72 MySQL pods ≈ 27 GiB**. Never use it here.

**Corroborating real-world reports:**
- [Issue #263](https://github.com/FudanSELab/train-ticket/issues/263): 17 services crashlooping on **7 CPUs / 27.3 GB RAM**; reporter said they had "not much more to give."
- [Issue #289](https://github.com/FudanSELab/train-ticket/issues/289): on **3 × (64 core / 128 GB)** servers, pod startup averaged **~150 s, some >400 s**; Spring context init alone took 121 s. Spring Boot 1.5.22 cold starts are the bottleneck.
- [SREGym](https://github.com/SREGym/SREGym) (UIUC, runs train-ticket among its apps) specifies **8 vCPU / 16 GB RAM for "SREGym-Lite"** on `kind` — and that is a *reduced* ("svelte") deployment with shortened Prometheus retention and optional Grafana/OpenSearch disabled.

**Verdict:**
- **16 GB laptop: not viable** for the full 41-service + SkyWalking + Prometheus stack. WSL2 defaults to 50% of host RAM (8 GB on a 16 GB machine), and you would need ~14 GB inside WSL while Windows still needs 4–6 GB. Even with aggressive request-trimming you would be swapping continuously, and JVM cold-start times would make 3000 episodes impossible.
- **24 GB: workable but tight.** Set `.wslconfig` `memory=20GB`, use all-in-one MySQL, scale nacos to 1 replica, MySQL to 1 replica, and patch app requests from 300Mi → ~150Mi.
- **32 GB: comfortable.** This is what I'd recommend for 3000 episodes.

**WSL2 config** ([reference](https://itnext.io/wsl2-tips-limit-cpu-memory-when-using-docker-c022535faf6f)):
```ini
# C:\Users\Laksh\.wslconfig
[wsl2]
memory=20GB
processors=8
swap=8GB
autoMemoryReclaim=gradual
```
Requires `wsl --shutdown` to take effect.

**None has any `mem_limit` or CPU constraint** — so compose will simply consume whatever the Docker VM has, which is *why* the docs say 24 GB. Compose is **not** lighter; it removes the scheduler's back-pressure but runs the same ~41 JVMs plus more MySQL instances.

**Does compose still give a service graph?** Only via `docker-compose-with-jaeger.yml`, and only a *trace-derived* one. Jaeger 1.15's own dependency graph requires the separate `spark-dependencies` batch job — the all-in-one image's in-memory store gives you `/api/dependencies` over a limited window at best. You would be building the graph yourself from raw spans.

**Fatal for your experiment:** compose gives you **no Chaos Mesh, no pod-level fault injection, no `kubectl`-driven episode control, and no kube-state-metrics restart counts.** Every field you want per-episode is harder.

**Recommendation: use Kubernetes (k3d). Do not use docker-compose.**

## PART B — Observability stack decision

### B1. SkyWalking vs OTel Collector + Tempo/Jaeger + Prometheus

**Your hard requirement:** per-edge service dependency graph with call rates and error ratios per time window, queryable programmatically.

#### Option 1 — SkyWalking (ships with Train Ticket)

**Topology GraphQL** ([Query Protocol docs](https://skywalking.apache.org/docs/main/latest/en/api/query-protocol/), [schema repo](https://github.com/apache/skywalking-query-protocol)). In 8.5.0 ([topology.graphqls@v8.5.0](https://raw.githubusercontent.com/apache/skywalking-query-protocol/v8.5.0/topology.graphqls)):

```graphql
getGlobalTopology(duration: Duration!): Topology
getServiceTopology(serviceId: ID!, duration: Duration!): Topology

type Topology { nodes: [Node!]!  calls: [Call!]! }
type Node { id: ID!  name: String!  type: String  isReal: Boolean! }
type Call { source: ID!  sourceComponents: [ID!]!
            target: ID!  targetComponents: [ID!]!
            id: ID!     detectPoints: [DetectPoint!]! }
```

`Duration` is `{ start, end, step }` with `step ∈ {MONTH, DAY, HOUR, MINUTE, SECOND}` — **this is your per-time-window knob**, and it maps cleanly onto an episode.

**Critically: `Topology.calls` carries no metrics.** You get edge *existence* and a `Call.id`. To get rate and error ratio you issue a second query per edge against ServiceRelation metrics, using `Entity{scope: ServiceRelation, serviceName, destServiceName}`.

**Exact metric names** — verified in both [v8.5.0 `core.oal`](https://raw.githubusercontent.com/apache/skywalking/v8.5.0/oap-server/server-bootstrap/src/main/resources/oal/core.oal) and [master `core.oal`](https://github.com/apache/skywalking/blob/master/oap-server/server-starter/src/main/resources/oal/core.oal) (identical set):

| Metric | OAL |
|---|---|
| `service_relation_client_cpm` | `from(ServiceRelation.*).filter(detectPoint == CLIENT).cpm()` |
| `service_relation_server_cpm` | `from(ServiceRelation.*).filter(detectPoint == SERVER).cpm()` |
| `service_relation_client_call_sla` | `from(ServiceRelation.*).filter(detectPoint == CLIENT).percent(status == true)` |
| `service_relation_server_call_sla` | `from(ServiceRelation.*).filter(detectPoint == SERVER).percent(status == true)` |
| `service_relation_client_resp_time` | `from(ServiceRelation.latency).filter(detectPoint == CLIENT).longAvg()` |
| `service_relation_server_resp_time` | `from(ServiceRelation.latency).filter(detectPoint == SERVER).longAvg()` |
| `service_relation_client_percentile` | `.percentile(10)` (`percentile2` on master) |
| `service_relation_server_percentile` | `.percentile(10)` |

**`cpm` = calls per minute (your call rate). `call_sla` = success percentage; error ratio = `1 − sla/100`.** Exactly what you asked for.

Service-level companions: `service_cpm`, `service_resp_time`, `service_sla`, `service_apdex`.

**Query API available in 8.5.0** ([metrics-v2.graphqls@v8.5.0](https://raw.githubusercontent.com/apache/skywalking-query-protocol/v8.5.0/metrics-v2.graphqls)): `readMetricsValue`, `readMetricsValues`, `readLabeledMetricsValues`, `sortMetrics`, `listMetrics`, `typeOfMetrics`, `readHeatMap`, `readSampledRecords`.

```bash
# UI is also on NodePort 30005, but query OAP directly — don't go through the UI
```

```graphql

```

#### Option 2 — OpenTelemetry Collector + servicegraph connector

**[servicegraphconnector](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/connector/servicegraphconnector/README.md)** — confirmed metric names:

| Metric | Type |
|---|---|
| `traces_service_graph_request_total` | Counter |
| `traces_service_graph_request_failed_total` | Counter |

⚠️ **`store.ttl: 2s` and `max_items: 1000` are far too small for Train Ticket.** Chains are deep and slow (issue #259: "Request response delay is too long"); client spans will expire before their server span arrives and land in `unpaired_spans_total`. Raise to `store.ttl: 30s`, `store.max_items: 100000`. **Always monitor `traces_service_graph_unpaired_spans_total` — if it is non-trivial your graph is silently wrong.**

**[spanmetricsconnector](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/connector/spanmetricsconnector/README.md)** — OTLP names `traces.span.metrics.calls`, `traces.span.metrics.duration`, `traces.span.metrics.events`; default dimensions `service.name`, `span.name`, `span.kind`, `status.code`, `collector.instance.id`. Note spanmetrics is **per-service RED, not per-edge** — it does not give you the graph. Use servicegraph for edges, spanmetrics for node features.

**Equivalent via Grafana Tempo's metrics-generator** ([docs](https://grafana.com/docs/tempo/latest/metrics-from-traces/service_graphs/), [PromQL examples](https://grafana.com/docs/tempo/latest/metrics-from-traces/service_graphs/metrics-queries/)) — same `traces_service_graph_*` family with `client`/`server` labels. (⚠️ **Unverified**: whether the OTel Java agent auto-instruments Spring Boot **1.5.22** — issue #289 shows at least `ts-assurance-service` is on 1.5.22, which is old. Test one service first.)

### B3. Connection-pool / thread-pool saturation — you were right to be unsure

**The honest answer: not obtainable from the stock deployment. But there are three real paths.**

**Why it doesn't work today** — verified from source:
- [`ts-order-service/pom.xml`](https://raw.githubusercontent.com/FudanSELab/train-ticket/master/ts-order-service/pom.xml) declares only `spring-boot-starter-data-jpa`, `mysql-connector-java`, `org.services:ts-common`, `jakarta.validation-api`. **No `spring-boot-starter-actuator`. - [`ts-order-service/src/main/resources/application.yml`](https://raw.githubusercontent.com/FudanSELab/train-ticket/master/ts-order-service/src/main/resources/application.yml) has **no `management:` section at all.**

So there is no `/actuator/prometheus`, and HikariCP's `hikaricp_connections_*` metrics have nowhere to go. (HikariCP *is* present transitively via `spring-boot-starter-data-jpa` — it just isn't exposed.)

**Path 1 — SkyWalking JVM thread metrics. Free, works today, no rebuild.**
The agent reports JVM telemetry automatically. Verified names from [`java-agent.oal`](https://raw.githubusercontent.com/apache/skywalking/master/oap-server/server-starter/src/main/resources/oal/java-agent.oal):

```
instance_jvm_thread_live_count
instance_jvm_thread_daemon_count
instance_jvm_thread_peak_count
instance_jvm_thread_runnable_state_thread_count
instance_jvm_thread_blocked_state_thread_count     ← saturation proxy
instance_jvm_thread_waiting_state_thread_count     ← pool-exhaustion proxy
instance_jvm_thread_timed_waiting_state_thread_count
instance_jvm_cpu, instance_jvm_memory_heap, instance_jvm_memory_heap_max
instance_jvm_young_gc_time / _count, instance_jvm_old_gc_time / _count
instance_jvm_class_loaded_class_count
```

**`blocked_state_thread_count` and `waiting_state_thread_count` are genuinely good saturation proxies.** When HikariCP exhausts its pool, requesting threads park in `TIMED_WAITING` on `getConnection()` — you will see it. When Tomcat's thread pool saturates, `live_count` pins at `maxThreads`. This is not as clean as `hikaricp_connections_pending`, but it is a real, causally-linked signal and **it costs you nothing**. Query via `readMetricsValues` with `entity:{scope: ServiceInstance, serviceName, serviceInstanceName}`.

This directly captures the wiki's **F5 fault ("thread pool resource exhaustion … asynchronous tasks in Basic-Info-Service with intentional saturation")** — so the benchmark's own fault taxonomy is observable this way.

**Path 2 — SkyWalking meter plugins.** The [supported-list](https://skywalking.apache.org/docs/skywalking-java/latest/en/setup/service-agent/java-agent/supported-list/) confirms tracing plugins for **HikariCP 3.x→4.x**, Druid, DBCP2, C3P0, plus **thread-pool meter plugins for Tomcat 7→10, Jetty 9.1→12, Undertow, Dubbo, Grizzly**, and **Micrometer Registry** integration. [SkyWalking 9.0.0](https://skywalking.apache.org/docs/main/next/en/changes/changes-9.0.0/) added JDK thread-pool metrics analysis (core size, max size, pool size, queue size) via `apm-jdk-threadpool-plugin`.

⚠️ **Caveat:** these are in **agent 9.x**, and the HikariCP entry is a *tracing* plugin (it traces `getConnection`), not necessarily a gauge exporter. To use them you must bump the initContainer from `8.8.0-alpine` to `apache/skywalking-java-agent:9.x` and bump the OAP to 9.x to match. **Unverified:** whether `apm-jdk-threadpool-plugin` covers HikariCP's internal pool specifically, and whether Spring Boot 1.5.22 + Tomcat 8.5 is within the meter plugin's supported range.

**Path 3 — add Actuator + Micrometer and rebuild. Definitive but expensive.**
Add to each `pom.xml`:
```xml
<dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-actuator</artifactId></dependency>
<dependency><groupId>io.micrometer</groupId><artifactId>micrometer-registry-prometheus</artifactId></dependency>
```
plus `management.endpoints.web.exposure.include: prometheus` and a `prometheus.io/scrape: "true"` pod annotation. Gives you the real thing: `hikaricp_connections_active/idle/pending/timeout_total`, `tomcat_threads_busy_threads`, `jvm_threads_states_threads`, `executor_pool_size_threads`, `executor_queued_tasks`.

Costs: `mvn clean package` across 41 modules, rebuild and push 41 images, and Spring Boot 1.5.x needs Micrometer 1.0.x + `spring-boot-actuator` (not the 2.x starter) — **non-trivial**. Only worth it if connection-pool saturation is a *headline* variable in your thesis rather than one feature among many.

**Recommendation: Path 1 now, Path 3 only if the field proves decisive.** Use `instance_jvm_thread_blocked_state_thread_count` + `instance_jvm_thread_timed_waiting_state_thread_count` + `instance_jvm_cpu` + `instance_jvm_memory_heap / instance_jvm_memory_heap_max` as your per-node saturation feature vector. Be explicit in your write-up that these are proxies, not direct pool gauges.

### C2. Storage for 3000 episodes × (41-node / ~100-edge graph + metric snapshots)

**Do the arithmetic first, because it reframes the question.**

3000 episodes × 100 edges × ~6 float fields ≈ **1.8 M numbers**. Plus 3000 × 41 nodes × ~10 features ≈ 1.2 M. At 8 bytes: **~25 MB.** With JSON overhead, maybe 150–400 MB.

**This is a small dataset.** It fits in RAM on any laptop. Anything that says "Spark", "data lake", "distributed", or "object store" is wrong by an order of magnitude. Optimise for **iteration speed and schema flexibility**, not scale.

**Head-to-head:**

| | Postgres + JSONB | DuckDB | Parquet on disk | Graph DB (Neo4j) |
|---|---|---|---|---|
| Setup | container + server | `pip install duckdb` | `pip install pyarrow` | container, heavy |
| Concurrent writes during collection | ✅ **excellent** | ⚠️ single-writer | ⚠️ one file per episode | ✅ |
| Query inside the graph JSON | ✅ JSONB ops + GIN index | ✅ JSON functions | ⚠️ needs unnest | ✅ native |
| Analytical scan speed | ⚪ fine at this size | ✅ **fastest** | ✅ fast | ❌ slow |
| Reads Parquet directly | ⚪ via FDW | ✅ **natively** | n/a | ❌ |
| Schema evolution mid-project | ✅ **best** (just add JSON keys) | ⚪ ALTER | ⚠️ awkward | ✅ |
| Survives a crash at episode 1,847 | ✅ **yes** | ⚠️ risk if writer dies | ✅ per-file | ✅ |
| Extra RAM on your constrained box | ~200 MB | **~0** (in-process) | **0** | ~1–2 GB ❌ |
| → PyTorch Geometric | query → build `Data` | query → build `Data` | read → build `Data` | awkward |

**A graph DB is the wrong tool here** and this is the most common mistake in this space. Neo4j is for traversing *one big graph*. You have **3000 independent tiny graphs** and you never traverse across them — every query is "give me episode N's edges" or "aggregate over all episodes." That is a relational/columnar workload, and Neo4j would cost you 1–2 GB of RAM you don't have.

#### 🔑 Recommendation: a two-tier split

**Tier 1 — collection: SQLite (or Postgres) as the write-ahead episode log.**

During a 3000-episode run lasting days, the thing that will actually hurt you is **a crash at episode 1,847**. Write each episode transactionally, immediately, with its status:

```sql
CREATE TABLE episodes (
  episode_id     INTEGER PRIMARY KEY,
  started_at     TIMESTAMP,
  ended_at       TIMESTAMP,
  status         TEXT,          -- running | ok | failed | discarded
  fault_spec     JSON,          -- chaos mesh manifest + target + params
  fault_type     TEXT,          -- denormalised for fast filtering
  target_service TEXT,
  workload_spec  JSON,          -- auto-query scenario mix, concurrency, duration
  graph          JSON,          -- {nodes:[...], edges:[{src,dst,cpm,err_ratio,p90,...}]}
  node_metrics   JSON,          -- per-pod cpu/mem/restarts/jvm threads
  slo            JSON,          -- observed error rate, latency
  notes          TEXT
);
CREATE INDEX idx_fault ON episodes(fault_type, target_service);
CREATE INDEX idx_status ON episodes(status);
```

Use **SQLite** if collection is single-process (simplest possible thing, zero daemons, file is trivially backed up). Use **Postgres + JSONB** if you run parallel collectors or want GIN indexes on the JSON. Postgres JSONB is the more powerful option; SQLite is the one you'll actually have working in 20 minutes.

**Tier 2 — analysis/training: export to Parquet, query with DuckDB.**

Once collection is done, flatten to two tidy Parquet files:

- `edges.parquet` — `(episode_id, src, dst, cpm, error_ratio, resp_time_avg, p90, ...)` → ~300k rows
- `nodes.parquet` — `(episode_id, service, cpu, mem_ws, restarts, jvm_threads_blocked, jvm_heap_ratio, ...)` → ~123k rows
- `episodes.parquet` — one row per episode with the labels

Then:
```python
import duckdb
con = duckdb.connect()
con.sql("SELECT * FROM 'edges.parquet' WHERE episode_id = 42")  # no import step
```
DuckDB reads Parquet in place with zero ingest, gives you full SQL over the flat tables, and adds **no resident memory** to your cluster box. This tier is throwaway and regenerable — all truth lives in Tier 1.

**Why not JSON-in-Parquet?** Keep the graph as *flat edge rows*, not a nested JSON column. Flat rows are what PyG wants anyway and what DuckDB aggregates fastest.

**→ PyTorch Geometric.** 3000 graphs × 41 nodes is **tiny** — use [`InMemoryDataset`](https://pytorch-geometric.readthedocs.io/en/latest/tutorial/create_dataset.html) and load the whole thing. In PyG ≥ 2.4, `self.save(data_list, self.processed_paths[0])` unifies `collate()` + `torch.save()`:

```python
class TTEpisodes(InMemoryDataset):
    def process(self):
        import duckdb, torch
        from torch_geometric.data import Data
        con = duckdb.connect()
        edges = con.sql("SELECT * FROM 'edges.parquet' ORDER BY episode_id").df()
        nodes = con.sql("SELECT * FROM 'nodes.parquet' ORDER BY episode_id").df()
        data_list = []
        for eid, g in edges.groupby('episode_id'):
            # build a STABLE global service->index map, not a per-episode one
            ...
            data_list.append(Data(x=x, edge_index=ei, edge_attr=ea, y=y))
        self.save(data_list, self.processed_paths[0])
```

**One design warning that will bite you:** build **one global `service → node_index` map** across all 3000 episodes and reuse it. If you index nodes per-episode, node 7 means a different service in different graphs and your GNN learns nothing. Related: when a fault kills a pod, that service may vanish from the SkyWalking topology entirely — decide deliberately whether absent nodes are **dropped** (variable node count) or **present with zeroed features and an `is_alive` flag** (constant node count). The latter is almost always what you want for fault localisation, and it makes `y` a clean per-node label.

**Recommendation: networkx as the in-memory model + pyvis for interactive inspection + Graphviz for publication figures.** networkx is the hub — it converts to PyG (`torch_geometric.utils.from_networkx`), to pyvis, and to Graphviz. One graph object, three outputs.

Useful pattern: render a **diff view** — baseline graph vs faulted graph, with edges coloured by Δerror-ratio. That is far more informative for debugging your pipeline than either graph alone, and it's ~20 lines with networkx + pyvis.

### C4. Purpose-built chaos-experiment result tracking — none of them replace your episode store

| Tool | What it stores | Replaces your store? |
|---|---|---|
| **Chaos Mesh** archives/dashboard | Experiment CRs + events, in SQLite/MySQL via gorm; REST API at `:2333`, Swagger at `/api/swagger/index.html` ([docs](https://chaos-mesh.org/docs/inspect-chaos-experiments/)) | ❌ Records **what was injected**, never **what happened to the system**. No telemetry, no graph. |
| **Litmus ChaosCenter** | Manifests + results in a DB, GraphQL backend ([docs](https://docs.litmuschaos.io/docs/architecture/chaos-control-plane)) | ❌ Same gap, plus it's a heavyweight control plane (MongoDB + GraphQL server) on a RAM-starved box. |
| **chaostoolkit journals** | JSON journal per run, RFC-3339 timestamps, [`chaostoolkit-reporting`](https://github.com/chaostoolkit/chaostoolkit-reporting) ([journal spec](https://chaostoolkit.org/reference/api/journal/)) | ⚠️ **Closest in spirit** — a portable JSON doc per experiment. But steady-state probes only; no service graph. |
| **Steadybit** | Commercial SaaS, experiment reports, open-source *extensions* | ❌ Commercial, cloud-oriented. |
| **Reliably** | ⚠️ **Could not verify current status** — search surfaced only Steadybit material. Treat as unknown. |

**Recommendation: don't try to replace your episode store with any of them — but *do* use Chaos Mesh's API as a cross-check.**

The architectural point: every chaos tool tracks the **independent variable** (the injected fault). None tracks the **dependent variable** (the resulting telemetry and topology). Your episode store exists precisely to join the two, and that join *is* your dataset.

Concretely: let Chaos Mesh own the fault CR, then copy the resolved spec + its `uid` + actual start/end timestamps into your `fault_spec` column. You get Chaos Mesh's ground truth on what actually ran (not what you intended — they differ when injection fails) without depending on its DB. The `chaostoolkit` journal is worth skimming as a **schema template** for `fault_spec`.
